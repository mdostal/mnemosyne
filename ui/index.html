      Operations
      
      
      
        Two distinct actions. Reindex shells out against the live Qdrant
        Cloud store and writes real data. Refresh config cache is purely
        local — it never touches Qdrant, config.toml, or the graph, and never
        deletes anything. Neither action, nor anything in this app, can wipe or drop a
        Qdrant collection.
      
      

      
      
        
      
          
      Reindex
      
          
      
            Chunk, embed and upsert the given path(s) into the selected lane's collection
            (swarm-memory index, default pruning — stale tail chunks of a
            shrunk file are cleaned up; nothing else is touched). Requires an explicit
            lane and at least one path — there is no "reindex everything" option.
          
      
          
      
            
      
              
              
            
      
            
      
              
              
            
      
            
            
      
            
      
          
      
        
      

        
      
          
      Refresh config cache
      
          
      
            Clears only this service's in-memory copy of swarm-memory config,
            so the next load re-reads it fresh. Does not touch Qdrant, config.toml,
            or the graph — nothing is deleted.
          
      
          
          
      
        
      
      
      
    
      
    
      
      
      Personas
      
      
      loading…
      
      
      
      loading…
      
      
      
        Every existing persona (global tiers: top-orchestrator,
        company-director, project-orchestrator) — fetched
        from the persona service on port 3141 (a different server than this UI's
        own, see lib/mnemosyne/server.ts). A persona's parent(s) render
        as pointer-only text (tier + scope ID) — the parent's actual content is
        never fetched or inlined here. Rows with a pending draft (agent-proposed
        or human-typed) are merged into the SAME list below, per
        .pHive/design/mnemosyne-persona-ux/synthesized/option-2.md
        §1/§3 ("one continuous list holds every persona identity — live and
        drafted").
      
      

      
      
      
        What do these terms mean?
        
      
          
      tier
      
          
      The four fixed levels a persona can sit at, in cascade order: top-orchestrator, company-director, project-orchestrator, code-architect.
      
          
      scopeId
      
          
      A human-assigned identity for this persona (a company/project/repo name) — never auto-detected.
      
          
      Parent(s)
      
          
      A pointer to where this persona's own content stops and a parent's begins ("query up, never copy down") — the parent's real content is never fetched or shown here, only named.
      
          
      sourceSummary
      
          
      What an agent read before proposing a draft — shown under the label "Why the agent proposed this" when reviewing a draft below. A human-typed draft has no sourceSummary, and never shows a fabricated one.

        Triage Review
        
      
        loading…
        
      
        loading…
        
      
        
        Two real, distinct sources (design-discussion.md §12.3): the
        Intake candidates table reads the live
        conversation_memory_intake Qdrant collection (cm-13's
        own scroll-based enumeration) and shows every entry's real
        scope-route status. Confirming a
        candidate_unconfirmed row appends ONE real
        ScopeRouteConfirmationEntry line to the shared
        triage-queue file — the ONLY filesystem write this panel ever
        performs — so a later cm-13 run routes that entry's
        content to the confirmed real scope instead of the safe
        meta default. Confirming an already-confirmed pair
        again is harmless (a duplicate line, never refused).
        Quarantine hits (secret-scan matches) are shown
        below for visibility only — no confirm/dismiss/delete/re-triage
        control exists for them anywhere in this panel; disposition remains
        a separate, not-yet-designed future decision.
      
        

      
        
        What do these statuses mean?
        
        
          
        no_candidate
        
          
        This intake entry carries no scope-route candidate at all — it routes to meta.
        
          
        candidate_unconfirmed
        
          
        A real scope-route candidate exists but has not been confirmed yet — the only status this panel's Confirm action ever accepts.
        
          
        candidate_confirmed_pending_distribution
        
          
        A real, on-disk confirmation exists, but cm-13 has not run since — not yet distributed.
        
          
        distributed
        
          
        A real distribution marker already references this entry — its content has already been routed.

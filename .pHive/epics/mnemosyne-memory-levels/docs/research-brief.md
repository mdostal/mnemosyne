# Research Brief — mnemosyne-memory-levels

All research done directly against this checkout on `feat/mnemosyne-memory-levels` (branched from `main`), reading source files, not inferring from prior docs alone.

## 0. The correction this epic exists to make

The operator's exact words (verbatim, ground truth for this whole epic — see design-discussion.md §1 for the full quote):

> "you have 3 levels listed as vector, graph, and files. those are the 2,3,4 -- 0 is the mnemosyne persona injection rules we are talking, 1 is the in repo persona overlay etc like the claude/agents/gemini/etc with the adapter ... then then your levels. the levels are not the orchestration or personal LEVEL -- coder isn't level 6. Each MEMORY STORE TYPE is a level ... The Orchestration MAPPINGs ARE LAYERS -- however, that is not MEMORY LAYERS but team/orchestration layers."

This corrects a real miscommunication that runs through this repo's own prior planning docs — not a scolding, a documented fact. Three different numbering schemes already exist in this codebase's docs/code, none of which is the operator's actual 5-level memory-store-type model:

1. **`docs/cba-memory-layers.md`'s "target architecture" (1-5)** — ways-of-working memory (1), hierarchical meta-knowledge/hive-memory (2), indexed docs/file store (3), code graph (4), semantic/vector search (5). Closer in spirit to the operator's real model than the other two, but numbered 1-5 (no "0"), and puts vector *last* rather than treating each store as a flat, order-independent level.
2. **`docs/layer-architecture-v2-plan.md` §1's "reconciled architecture" table ("Layer 1/2/3")** — calls the harness meta-file mechanism "Layer 1," calls the *combination* of hive-memory-KG-plus-vector "Layer 2," and calls the *combination* of Graphify's doc-index-plus-code-graph "Layer 3." This table conflates two different axes in one column: it numbers memory-store types (KG, vector, graph, docs) using the same "Layer N" vocabulary the code literally uses for the role/tier hierarchy (`lib/mnemosyne/layer1/` — see §2 below), and it merges genuinely distinct store types (KG vs. vector; docs vs. code-graph) into single numbered rows.
3. **`lib/mnemosyne/layer1/`'s own module name and the retrieval cascade's `layers/` config surface** — a *third*, independent use of the word "layer": `layer1/` is the harness-meta-file-sync package (tiers, Level 0, block-splicing), while `lib/mnemosyne/layers/` (no "1") is the pluggable *retrieval adapter* registry (vector/file/graphify/code-graph/hive-memory/crossref-linker/keyword — see §3). These are two different, real, both-already-shipped things that happen to share almost the same directory name.

None of these three is wrong on its own terms — each was a real, deliberate design at the time it was written. But none of them is the operator's actual model (memory-store-TYPE is the level; the 4-tier orchestration hierarchy and the retrieval-cascade config are separate axes entirely), and their vocabulary collisions (three different "Layer 1"/"layer" meanings already live in this one repo) are very likely the proximate cause of the miscommunication this epic exists to fix. §7 of design-discussion.md documents this as a named, resolved judgment call rather than silently reconciling it.

## 1. The 4-tier orchestration hierarchy — confirmed separate axis, must never be relabeled

`lib/mnemosyne/layer1/tiers.ts` (`TIERS` const, lines 24-29): `top-orchestrator` → `company-director` → `project-orchestrator` → `code-architect`. This is the **team/orchestration** hierarchy the operator's own words name explicitly ("The Orchestration MAPPINGs ARE LAYERS -- however, that is not MEMORY LAYERS but team/orchestration layers"). Each tier gets different `TierContent` (`sections`), composed by `getPersonaContent` (`persona.ts`) and spliced into harness files by `sync.ts`. **This epic makes zero change to `tiers.ts`'s tier model, its 4 tier IDs, or any UI/doc copy that describes them as tiers** — it only ensures nothing calls a tier a "level" or a level a "tier" anywhere this epic's own scope touches.

## 2. Level 0 and the existing "Layer 1" harness-sync mechanism — exact mechanics

`lib/mnemosyne/layer1/level0.ts`: `readLevel0Content(level0Path = DEFAULT_LEVEL0_PATH)` reads `~/.mnemosyne/level0-rules.md` **fresh on every call** (no caching), throws loudly if missing (`level0.ts:24-33`). This file is operator-authored, global, outside any repo — exactly the operator's stated Level 0 ("mnemosyne's own injection rules ... added into a repo's agent files").

`lib/mnemosyne/layer1/sync.ts`'s `buildManagedBody(tier, scopeId, repoRoot, level0Content)` (lines 57-61) composes `[level0Content.trim(), '', '---', '', tierMarkdown.trim()]` — Level 0 **always first, verbatim**, then tier/persona markdown from `getPersonaContent`. `syncHarnessFile` (lines 70-101) locks (`withLock`, TOCTOU-safe), reads the existing target file, splices via `block.ts`'s `spliceManagedBlock`, writes. `syncAllHarnesses` (lines 107-116) fans this out to every `HARNESS_TARGETS` entry.

`lib/mnemosyne/layer1/harness.ts`'s `HARNESS_TARGETS` (lines 32-36) — the **full, exact list of harness-native files this repo already targets**: `CLAUDE.md` (Claude Code), `AGENTS.md` (Codex), `GEMINI.md` (Gemini CLI). Adding a 4th harness is a one-line addition here, nothing else changes (module doc comment, lines 3-7).

`lib/mnemosyne/layer1/block.ts`: `BLOCK_START`/`BLOCK_END` (lines 17-19) are HTML-comment markers (`<!-- mnemosyne:layer1:begin -->` / `<!-- mnemosyne:layer1:end -->`) delimiting a managed region. `spliceManagedBlock` (lines 37-67) is idempotent: no file → block is the file; file with no markers → block appended after existing (human) content, preserved verbatim; file with markers → only the text between the **last** matched pair is replaced (deliberately `lastIndexOf`, not `indexOf` — a documented fix for a stray-leading-marker edge case, lines 44-53), everything else byte-identical.

**Confirmed: today's "Layer 1" (the code module name, the doc's terminology, and the operator's stated Level 1 concept) already IS the exact mechanism that generates content and splices it into `CLAUDE.md`/`AGENTS.md`/`GEMINI.md`.** What's missing is the operator's specific new ask: a canonical, git-committed, human-readable `mnemosyne.md` source file (today, Level 1's content is generated purely from TypeScript — `tiers.ts`'s hardcoded `TIER_CONTENT`/`MANDATE_SECTIONS` plus YAML `Persona` records — there is no markdown file a human edits directly as "the" Level 1 source), and an install mechanism to "lock that in easy."

**`MANDATE_SECTIONS`** (`tiers.ts` lines 110-126) is the closest existing analog to what the operator is describing for `mnemosyne.md`: harness-agnostic, tier-agnostic, mandatory content ("recall on entry," "remember on exit," "flight-status awareness") that every tier's rendered output includes identically. It is currently a hardcoded TS constant, not an editable file.

## 3. The retrieval-cascade config surface — confirmed genuinely separate mechanism

`lib/mnemosyne/layers/` (no "1" — distinct directory from `layer1/`) holds `LayerAdapter` implementations: `VectorLayerAdapter`, `FileLayerAdapter`, `GraphifyLayerAdapter`, `CodeGraphLayerAdapter` (legacy, being phased out per `la-10`'s A/B benchmark — `docs/layer-architecture-v2-plan.md` §7), `HiveMemoryLayerAdapter`, `CrossRepoLinkerAdapter`, `KeywordLayerAdapter`. `registry.ts`'s `registerBuiltinLayers` (lines 71-121) registers each by name; `config.ts`'s `resolveLayerStackConfig` (lines 122-161) resolves which are active and in what order, from (in priority order) explicit config → `MNEMOSYNE_LAYERS` env → `mnemosyne.layers.json` → a hardcoded default (`graphify, vector, file`, soft-falling-back to `code-graph, vector, file` when the `graphify` binary isn't on `PATH`, `config.ts:68-79`, `108-120`).

`MnemosyneClient.getConfiguredLayers()` (`client.ts:263-265`) returns `{layer, writable}[]` for whatever the resolved stack contains — this is exactly what `GET /layers` on `lib/mnemosyne/server.ts` returns (`server.ts:228-247`, `sendJson(res, 200, { layers: client.getConfiguredLayers() })`), and exactly what `ui/app.js`'s `loadPersonaLayerStack()` (lines 1346-1387) renders into the existing "Memory Layer Stack" panel (`ui/index.html:276-294`) under the heading `Memory Layer Stack`.

**This is a runtime *retrieval-mechanics* config: which backends does a `recall()`/`remember()` call cascade through, in what order, right now.** It answers a different question than the operator's 5-level model, which answers "what kinds of memory-store TYPES exist, period" (a taxonomy, largely static) rather than "which of them is active in this process's cascade, right now" (a runtime resolution). Confirmed structurally distinct in three ways:

- **Levels 0 and 1 have no retrieval-cascade participation at all.** Level 0/1's mechanism (`layer1/sync.ts`) writes files at sync time; it is never queried by `recall()`/`remember()`, never appears in `registry.ts`, never appears in `GET /layers`'s output. The retrieval cascade literally cannot represent levels 0/1 today — not a bug, a structural fact: they are a *file-generation* mechanism, not a *runtime-query* mechanism.
- **Some cascade adapters don't correspond to any one of the operator's 5 levels.** `hive-memory` reads plugin-hive's own `kg.sqlite` + memory-file trees (`HiveMemoryLayerAdapter.ts:1-26`) — an external system Mnemosyne only reads, never owns; it isn't a Mnemosyne-owned store type the way levels 0-4 are. `crossref-linker` is a derived, multi-repo *capability* built by scanning file content across several repos' roots (`CrossRepoLinkerAdapter.ts:1-41`) — not a distinct storage location, a computed cross-reference over existing file/AST data.
- **Multiple cascade adapters can serve one level.** `keyword` (`KeywordLayerAdapter`) shells to `swarm-memory grep` "against the same remote Qdrant-indexed corpus 'vector' searches" (`registry.ts:111-119`, verbatim comment) — a different *retrieval mode* (exact/keyword vs. semantic) over the *same* underlying store as `vector`, not a 6th store type. Likewise `code-graph` and `graphify` are two competing *implementations* of the same store type (level 2, graph), with `graphify` now the soft-default and `code-graph` the fallback (`config.ts`'s doc comment, lines 9-31).

## 4. Level 2 (graph) — Graphify + legacy code-graph

`GraphifyLayerAdapter.ts` (`layer = 'graphify'`, constructor line 125-128): shells to the `graphify` CLI, reads/builds `<repoRoot>/graphify-out/graph.json`, repo-scoped by construction (`repoRoot` option, defaulting to `process.cwd()`). `la-10`'s A/B benchmark (`docs/layer-architecture-v2-plan.md` §7) found the legacy `CodeGraphLayerAdapter` (shared, unscoped `~/.local/share/swarm-memory/graph.sqlite`) returns **zero nodes from this repo** while `graphify` indexed 1470 real nodes/2484 links from this repo's own source — `graphify` is the soft-configured default (`config.ts:68-69`) whenever the binary is on `PATH`; `code-graph` is the fallback, kept registered but not GO'd for removal yet.

## 5. Level 3 (vector) — confirmed

`VectorLayerAdapter.ts` (`layer = 'vector'`): shells to `swarm-memory recall <query> --json` against the Qdrant Cloud-backed corpus (`layers/README.md` §"Vector Layer"). `keyword` (`KeywordLayerAdapter`, same README not yet updated for it, but `registry.ts:111-119`'s comment is explicit) is a sibling retrieval mode over the same corpus, exact/substring rather than semantic.

## 6. Level 4 (file doc store) — confirmed, and confirmed to have NO index today

`FileLayerAdapter.ts` (`layer = 'file'`): a raw, un-indexed filesystem walk. `recall()` (lines 30-116) does a full recursive directory walk (`walk()`, lines 118-135, skipping `.git`/`node_modules`/`dist`/`build`/`coverage`) **on every single call**, reading every file's full content and doing a plain `line.includes(normalizedQuery)` substring match per line — "there is no indexing step, no embedder, and no cached hash store" (`layers/README.md` §"File Layer," verbatim). This is exactly the gap the operator's ask targets: *"the file doc store (and we should do an index of the contents OF the file doc store so we can index areas of it for a quick search as well)."* No sub-index, manifest, cache, or area/topic concept exists anywhere in `FileLayerAdapter.ts` or its test suite (`lib/mnemosyne/layers/__tests__/FileLayerAdapter.test.ts`) today — confirmed by reading the whole file; it has zero persisted state between calls.

## 7. The UI panel + route this epic must rework — exact current shape

`ui/index.html:276-294`: `<section id="persona-layer-stack" class="panel panel-wide">`, `<h2>Memory Layer Stack</h2>`, hint text reading *"The currently configured memory layer stack — not a persona list. Read-only introspection via the existing `GET /layers` route, shown in cascade order."* Table columns: `#`, `Layer`, `Writable`.

`ui/app.js:1346-1387`, `loadPersonaLayerStack()`: fetches `mnemosyneClientApiBase() + "/layers"` (`app.js:1202`, resolves to `http://127.0.0.1:3141` by default — `lib/mnemosyne/server.ts`'s `MNEMOSYNE_PORT`), renders each `{layer, writable}` entry as a numbered row.

`lib/mnemosyne/server.ts:228-247`: `GET /layers` — `applyPersonaCors(req, res); return sendJson(res, 200, { layers: client.getConfiguredLayers() });`. CORS is scoped to `UI_ORIGINS` (`http://127.0.0.1:8477`, `http://localhost:8477` — the standalone UI's real, known origins on `src/server.mjs`, lines 100-106), never a wildcard.

**This panel today shows exactly the retrieval-cascade adapter list (§3), not the operator's 5-level model.** It correctly calls itself "not a persona list" but does not, and structurally cannot without a schema change, distinguish "which of the 5 canonical memory levels exist" from "which retrieval adapters are active right now" — because `GET /layers`'s response shape (`ConfiguredLayerInfo[]`, `{layer, writable}`) is `client.getConfiguredLayers()`'s cascade output, one-to-one.

## 8. Install-script / CLI conventions already established (for the mnemosyne.md install mechanism)

`bin/mnemosyne-install-hooks` and `bin/mnemosyne-install-git-hooks` (both real, `package.json`'s `bin` field, lines 10-17) are this repo's existing "install" pattern: idempotent, re-computes and updates in place rather than duplicating, `--yes`/flag-gated, safe to re-run after a move/re-clone (`mnemosyne-install-hooks` doc comment, lines 1-16). `bin/mnemosyne-persona.mjs` already has a `sync --repo <path> --tier <tier> --scope-id <id> [--dry-run]` verb that calls `syncAllHarnesses`/`syncHarnessFile` directly (confirmed via `pf-04`'s dry-run work) — this is already, today, the "install Layer 1 content into this repo's harness files" verb; it just doesn't yet compose a `mnemosyne.md` source.

## 9. Reindex/index-building precedent (for the Level 4 sub-index)

`ui/app.js:1025-1127` — the existing "Operations panel" `Reindex` feature (`POST /index` on `src/server.mjs`, a *different* server than `lib/mnemosyne/server.ts`) is this repo's one existing precedent for an operator-triggered "(re)build an index over content" UX: a form (lane + paths), a confirm-before-run guard (real write against live Qdrant), pass/fail status reporting. Useful shape to mirror for a Level 4 sub-index rebuild trigger, not a mechanism to literally reuse (different store, different server).

`la-03-graphify-doc-index` (complete, `.pHive/epics/mnemosyne-layer-architecture-v2/stories/la-03-graphify-doc-index.yaml`) is a **different, already-shipped** capability: it extends `GraphifyLayerAdapter` to surface markdown doc nodes (with line-number `source_location`) from Graphify's own `graph.json` — Graphify's index of docs, not a new index over `FileLayerAdapter`'s raw-walk target. **This epic's Level 4 sub-index is NOT a duplicate of `la-03`**: `la-03` indexes docs *through Graphify's AST graph* (level 2's mechanism); this epic indexes the *raw, brute-force file layer* (level 4, `FileLayerAdapter`, which has zero relationship to Graphify or `graph.json`) so area-scoped search works even in a repo with no Graphify install, and so level 4 stops being purely-linear-scan-only. Documented explicitly as a resolved judgment call in design-discussion.md §7 to avoid this looking like unintentional duplication of already-shipped work.

## 10. Prior epics already touching this exact UI section — do not re-litigate what they settled

`mnemosyne-persona-wizard`'s `pw-04-layer-stack-visibility` (complete, merged) built the *current* "Memory Layer Stack" section specifically to reuse `GET /layers` "as-is" and to keep Level 0 "genuinely view-only (no edit affordance anywhere)" — both explicit, tested, shipped decisions. This epic's UI rework must not regress either: `GET /layers` stays exactly as it is (reused, not replaced — see design-discussion.md §5's routing decision), and Level 0 stays view-only-with-a-pointer everywhere this epic's UI work touches it.

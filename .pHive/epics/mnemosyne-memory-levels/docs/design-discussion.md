## 0. Prelude

No PRIOR DECISIONS/NORTH STAR block found scoped to this exact question. `docs/layer-architecture-v2-plan.md` §1's "reconciled architecture" table is the closest prior doc, and — per research-brief.md §0 — it is itself part of what this epic corrects, not a settled precedent to build on unmodified.

## 1. Goal

Correct and build out Mnemosyne's memory-level model per the operator's own, exact, corrected words (verbatim — this is ground truth for the whole epic, not a paraphrase or a starting guess):

> "you have 3 levels listed as vector, graph, and files. those are the 2,3,4 -- 0 is the mnemosyne persona injection rules we are talking, 1 is the in repo persona overlay etc like the claude/agents/gemini/etc with the adapter (we should make our own mnemosyne.md and then include it INTO the others with an install script or something to lock that in easy or just drop in all of the TYPES (gemini, claude,agents etc) and have it include mnemosyne. then then your levels. the levels are not the orchestration or personal LEVEL -- coder isn't level 6. Each MEMORY STORE TYPE is a level -- so 0 comes from mnemosyne directly and has to be added to things from mnemosyne itself. then we have a repo level agent overview (default agent integration with their .md instructions) then we have the added graph, the vector, the file doc store (and we should do an index of the contents OF the file doc store so we can index areas of it for a quick search as well) EACH TYPE is a layer. The Orchestration MAPPINGs ARE LAYERS -- however, that is not MEMORY LAYERS but team/orchestration layers."

**The canonical model this epic builds, decomposed from the quote above:**

| Level | What it is | Store type | Today's mechanism |
|---|---|---|---|
| **0** | Mnemosyne's own injection rules, sourced directly from Mnemosyne, added into a repo's agent files | operator-global rules file | `~/.mnemosyne/level0-rules.md`, `level0.ts` — already real, unchanged by this epic |
| **1** | The in-repo agent overlay — harness-native `.md` instruction files | repo-committed instruction files | `CLAUDE.md`/`AGENTS.md`/`GEMINI.md` via `layer1/sync.ts` — already real; this epic ADDS a canonical `mnemosyne.md` source + install mechanism |
| **2** | Graph | code/doc structure graph | `graphify`/`code-graph` adapters (`lib/mnemosyne/layers/`) — already real |
| **3** | Vector | semantic embedding store | `vector`/`keyword` adapters — already real |
| **4** | File doc store | raw filesystem content | `FileLayerAdapter` — already real, has **no index**; this epic ADDS a sub-index |

**Explicitly, permanently OUT of this numbering**: the 4-tier `top-orchestrator`/`company-director`/`project-orchestrator`/`code-architect` orchestration hierarchy (`tiers.ts`). It is a separate axis — "team/orchestration layers," the operator's own term — and nothing in this epic's scope may relabel it with these level numbers, call a tier a "level," or otherwise blur the two anywhere its work touches UI copy or docs.

## 2. What exists today (see research-brief.md for full file:line detail)

- **Levels 0 and 1's underlying mechanism is already real and shipped** (`la-01`/`la-00`, epic `mnemosyne-layer-architecture-v2`): `level0.ts` + `layer1/sync.ts`/`block.ts`/`harness.ts` compose Level 0 verbatim + tier/persona content into `CLAUDE.md`/`AGENTS.md`/`GEMINI.md`, idempotently, lock-safe. What's missing for Level 1 specifically: a canonical, git-committed `mnemosyne.md` source file (today Level 1's content is generated purely from TypeScript — `TIER_CONTENT`/`MANDATE_SECTIONS`/YAML `Persona` records — there's no markdown file a human edits directly), and an "install mechanism ... to lock that in easy."
- **Levels 2-4's underlying stores are already real** (`graphify`/`code-graph`/`vector`/`keyword`/`file` adapters, `lib/mnemosyne/layers/`). Level 4 (file) has genuinely zero indexing — confirmed by reading the whole adapter, a full brute-force walk+grep on every call.
- **The retrieval-cascade config (`GET /layers`, `MNEMOSYNE_LAYERS`) is a real, separate, already-shipped mechanism** answering "which backends does `recall()` cascade through right now" — not the same question as "what memory-store types exist" (research-brief.md §3). It cannot represent levels 0/1 at all (they never participate in `recall()`), and it contains adapters (`hive-memory`, `crossref-linker`) that don't map onto any single one of the 5 canonical levels, plus adapters (`keyword`, `code-graph`) that are alternate retrieval modes/implementations over a level the model already names, not additional levels.
- **The UI panel this epic must rework already exists** and, today, shows the retrieval cascade under the label "Memory Layer Stack" (`ui/index.html:276-294`, `ui/app.js:1346-1387`, `GET /layers` on `lib/mnemosyne/server.ts:228-247`) — built by `pw-04-layer-stack-visibility` explicitly to reuse `GET /layers` "as-is." That decision does not need to be undone; it needs a second, clearly distinct section/route added alongside it, per §5 below.
- **Three prior, independent uses of the word "layer/Layer N" already coexist in this codebase** (research-brief.md §0) — a documented, real source of the miscommunication this epic corrects, not invented for this doc.

## 3. Proposed approach — Level 0

**No change.** Level 0's mechanism (`level0.ts`, `~/.mnemosyne/level0-rules.md`) already matches the operator's description exactly: "0 comes from mnemosyne directly and has to be added to things from mnemosyne itself." This epic's only Level-0-adjacent work is documentation — recording it explicitly as memory-level 0 in the canonical taxonomy module (§6, story `ml-01`) so it's named consistently alongside 1-4, not re-implementing anything.

## 4. Proposed approach — Level 1 (mnemosyne.md + install mechanism)

**4a. `mnemosyne.md` is a new, repo-root, git-committed canonical source file** — Mnemosyne's own "how to work with memory in this repo" content, harness-agnostic and (initially) tier-agnostic. Its natural, low-risk seed content is today's `tiers.ts` `MANDATE_SECTIONS` constant (research-brief.md §2): already exactly this shape (harness-agnostic, tier-agnostic, currently hardcoded TS rather than an editable file) — moving it into an editable markdown file is a direct realization of the operator's ask, not new content invention.

**4b. Composition order, extending the existing Level-0-first rule:** Level 0 (operator-global, verbatim, first) → Level 1 (`mnemosyne.md`, repo-owned, second) → tier/persona content (unchanged, third). This is an additive extension of `buildManagedBody`'s existing three-part join (research-brief.md §2), not a redesign — the same `spliceManagedBlock`/`withLock` mechanism handles the larger body unmodified.

**4c. Install mechanism — chosen: full-content splice via the existing sync pipeline, not a native per-harness `@include` directive.** The operator offered two shapes: (a) an install script that includes `mnemosyne.md`'s content into each harness file, or (b) drop-in per-harness-TYPE files that each *reference* `mnemosyne.md` (e.g. a native include/import syntax). Resolved in favor of (a) — see §7.1 for the full reasoning; short version: (a) reuses the already-tested, already-harness-agnostic `spliceManagedBlock`/`syncHarnessFile` mechanism with zero new per-harness-format logic, while (b) would require confirming and maintaining three different harnesses' native include syntax (only one of which — Claude Code's `@path` import — is independently known to exist; Codex/AGENTS.md and Gemini/GEMINI.md were not confirmed to support an equivalent during `la-01`'s own harness research, research-brief.md §2), a real, currently-unverified dependency this epic should not silently assume.

**4d. The install mechanism reuses the existing CLI verb, not a new bin script.** `bin/mnemosyne-persona.mjs sync` already is, today, "the install-Layer-1-content-into-this-repo's-harness-files verb" (research-brief.md §8). Extending it to also read `mnemosyne.md` is a change to what content `sync` composes, not a new install surface — matches this repo's own memory of "no bespoke god wiring" (ways-of-working) far better than inventing `bin/mnemosyne-install-mnemosyne-md` alongside an already-existing sync verb that does the same job.

## 5. Proposed approach — Level 2/3/4 UI + route rework (the epic's core architectural decision)

**Decision: add a new, parallel `GET /memory-levels` route and a new, adjacent UI section — do not extend or repurpose `GET /layers`.**

Reasoning, grounded in research-brief.md §3/§7 rather than asserted:

- `GET /layers`'s response shape (`{layers: [{layer, writable}]}`) IS `client.getConfiguredLayers()`'s cascade output — a **runtime resolution** (what's active right now, in what order, per `MNEMOSYNE_LAYERS`/`mnemosyne.layers.json`/soft-default). The 5-level model is a **largely-static taxonomy** (what store types exist, period — level 0/1 don't even participate in a `recall()` cascade at all, so they are structurally *unrepresentable* inside `GET /layers`'s existing shape without a breaking, semantically-dishonest change).
- Overloading `GET /layers` to also carry levels 0/1 would either (a) fabricate fake "writable" cascade entries for a file-sync mechanism that has no `recall()`/`remember()` relationship, or (b) require two different object shapes inside one array, discriminated ad hoc — both worse than a second, honestly-named route.
- This directly matches a pattern this repo's own prior epics already established and got operator sign-off on: `pf`/`pw`'s design discussions repeatedly flag "these are two different data models, never merge them into one list" (persona content vs. layer-stack config, `mnemosyne-persona-foundation`'s design-discussion.md Risks table; persona list vs. layer-stack section, `pw-04`'s own acceptance criteria). Extending `GET /layers` to also mean "the 5 canonical levels" would be exactly the kind of merge those epics deliberately avoided elsewhere.
- `GET /layers` itself is explicitly **not to be touched** by this epic in behavior or shape — `pw-04-layer-stack-visibility` shipped it, tested it, and the persona panel already depends on it rendering the retrieval cascade specifically. A regression test (`ml-07`) proves this.

**UI treatment:** the existing "Memory Layer Stack" panel (`ui/index.html:276-294`) is **renamed** "Retrieval Layer Stack" with revised hint copy making explicit that it is the runtime `recall()`/`remember()` cascade, not the canonical memory-level taxonomy — no change to its data source (`GET /layers`, unchanged) or its `loadPersonaLayerStack()` fetch logic. A new, visually and structurally distinct section, "Memory Levels (0-4)," is added alongside it, fetching the new `GET /memory-levels` route, rendering each of the 5 canonical levels with: level number, label, store type, and either "configured"/pointer-to-source (levels 0/1: path to `level0-rules.md`/`mnemosyne.md`) or "active in current retrieval cascade: yes/no" cross-referenced from the *same* `getConfiguredLayers()` data levels 2-4 already have available (without merging the two sections into one list — the cross-reference is a read, not a merge). Both sections carry explicit copy stating neither is the team/orchestration tier hierarchy, per the operator's own emphatic distinction.

**`GET /memory-levels`'s own data source:** the new canonical taxonomy module (`ml-01`, §6 below) is static (5 entries, known at build time) plus two live checks: (a) does `mnemosyne.md`/`~/.mnemosyne/level0-rules.md` exist on disk right now (levels 0/1), (b) is a level-2/3/4-backing adapter name present in `client.getConfiguredLayers()`'s *current* resolved cascade (levels 2-4 — a read of already-computed data, not a new resolution). No new adapter/registry work — this route is read-only introspection composing two already-real data sources, mirroring `GET /layers`'s own "never a hardcoded/stale echo" posture (`server.ts:229-231`).

## 6. Proposed approach — Level 4 sub-index

**A new, standalone index over `FileLayerAdapter`'s target directory, keyed by "area"** (directory/topic/heading — the operator's own word, "index areas of it for a quick search"), consulted by `recall()` before falling back to the existing full-walk-and-grep, never replacing it (a stale or missing index degrades to today's exact behavior, never a silent gap). Concretely: a rebuildable, on-disk JSON manifest (mirroring `FileLayerAdapter`'s own provenance shape — `sha256` content hash per indexed unit, matching the adapter's existing `content_hash` field exactly, so staleness is detectable the same way the adapter already computes hashes today) mapping an "area" (top-level directory, or a heading extracted from markdown files, kept intentionally simple rather than inventing a topic-clustering algorithm — see §7.4) to the set of files/line-spans under it. A query scoped to (or matching) a known area narrows the walk to that area's file set instead of walking the whole tree; an unscoped or unmatched query falls through to the existing full walk unmodified.

This is confirmed, by direct comparison (research-brief.md §9), to be a **different** capability from the already-shipped `la-03-graphify-doc-index` (which indexes docs through Graphify's own AST graph, a level-2 mechanism) — this epic's sub-index is over the level-4 raw file layer specifically, and works with zero Graphify dependency.

## 7. Resolved judgment calls (solo-planning, no interactive operator available — reasoning stated for each, mirroring `mnemosyne-persona-wizard`'s "Resolved Ambiguities" convention)

**7.1 — Level 1 install mechanism: full-content splice via the existing sync pipeline, not per-harness native includes.**
The operator offered both shapes as acceptable ("Operator is open to either shape"). Chosen: extend the existing `spliceManagedBlock`/`syncHarnessFile` pipeline to also compose `mnemosyne.md`'s content into the managed block (full-content splice, exactly like Level 0 and tier content already are), rather than a thin per-harness pointer/include directive. Reasoning: (1) zero new per-harness-format logic — the existing mechanism is already proven harness-agnostic by construction (research-brief.md §2, `harness.ts`'s own doc comment: "piggyback on native harness files, don't invent a new loader"); a native-include approach would require verifying and maintaining three different, harness-specific include syntaxes, only one of which (Claude Code's `@path` import) this session could confirm exists — Codex/Gemini equivalents were not confirmed by `la-01`'s own prior harness research and are not re-verified here; (2) `mnemosyne-persona-foundation`'s design-discussion.md §7a already names the thin-pointer approach as "a legitimate future adapter variant, not required now" — this epic treats that framing as still correct and does not relitigate it; (3) reusing the pipeline means the new content gets the same idempotency/locking/dry-run guarantees Level 0 and tier content already have tested, with no new correctness surface. The thin-pointer/native-include variant remains available as a future adapter (per persona-foundation's own framing) if a harness's native include mechanism is later confirmed and preferred — not built here.

**7.2 — `mnemosyne.md`'s existence is optional, not hard-required, unlike Level 0.** Level 0 hard-fails sync when missing (deliberate — it's operator-global and must never be silently omitted, `level0.ts:24-33`). `mnemosyne.md` is new, per-repo, opt-in content this epic is introducing; every existing repo lacks one on day one. Hard-requiring it would break every existing harness sync the moment this epic ships, in every already-adopted repo. Resolved: missing `mnemosyne.md` means Level 1's content is simply omitted from the composed body (Level 0 + tier content compose exactly as they do today), not a hard failure — a repo adopts Level 1 by adding the file, not by being forced to.

**7.3 — New parallel route (`GET /memory-levels`), never extend/repurpose `GET /layers`.** Full reasoning in §5 above. Restated briefly here because it is this epic's single highest-leverage architectural decision: the retrieval cascade and the 5-level taxonomy are different data models answering different questions, and this repo's own prior epics already established "never merge two different data models into one list" as a standing convention (persona-foundation/persona-wizard's own risk tables) — this decision applies that same convention here rather than reinventing the reasoning.

**7.4 — Level 4 sub-index granularity: directory + markdown-heading based, not a topic-clustering/embedding-based scheme.** The operator's ask ("index areas of it for a quick search") does not specify a granularity. Resolved in favor of the simplest mechanism that delivers real narrowing value without adding a new dependency: top-level (and one level of nested) directory as the primary "area" unit, plus markdown `#`/`##` heading text as a secondary, finer-grained unit for `.md` files specifically (mirroring, at a much simpler level, how Graphify's own doc-index already treats markdown headings as addressable units, per `la-03`'s shipped work — a proven-useful granularity choice in this exact codebase, not invented from nothing). Explicitly NOT building: semantic/embedding-based area clustering (that's what level 3, vector, already does — duplicating it inside level 4 would blur the two levels this epic exists to keep distinct) or a new taxonomy/ontology the operator would need to hand-maintain. If directory+heading granularity proves insufficient in practice, a richer scheme is future work, not a blocker for this epic's v1.

**7.5 — `hive-memory` and `crossref-linker` are not assigned a 6th/7th canonical level.** Neither corresponds to a Mnemosyne-owned store type the operator's 5-level model names: `hive-memory` reads an *external* system (plugin-hive's own `kg.sqlite`/memory files) Mnemosyne never writes to; `crossref-linker` is a *derived*, computed capability (cross-repo identifier matching) built over existing file/AST data, not a storage location of its own. Resolved: both stay exactly where they already are — participants in the retrieval cascade (`GET /layers`, unchanged) — and are explicitly NOT listed in the new `GET /memory-levels` taxonomy. If the operator later wants `hive-memory` folded into the canonical model (e.g. as a variant of level 2, since KG triples are graph-shaped), that is a real, separate decision flagged in §8 below, not guessed here.

**7.6 — `code-graph` (legacy) is documented as level 2's retired-but-still-registered implementation, not removed.** `la-10`'s A/B benchmark already recommended GO on eventually retiring it (`docs/layer-architecture-v2-plan.md` §7) but explicitly scoped that retirement as "a separate, later story" not bundled into `la-10` itself. This epic's taxonomy work (`ml-01`) documents `code-graph` as level 2's legacy/fallback implementation (alongside `graphify` as the current default) rather than pretending it doesn't exist or silently removing it — actually retiring it is out of this epic's scope, unchanged from `la-10`'s own stated boundary.

## 8. Open questions — not resolved here (flagged, not guessed past)

**OQ1 — Should `hive-memory` (plugin-hive's KG) eventually get its own canonical memory level, or a documented sub-type of level 2?** §7.5 keeps it out of the 5-level model for now on the grounds that it's an external, read-only-integrated system rather than a Mnemosyne-owned store. This is a real product-shape question (is Mnemosyne's memory-level taxonomy meant to describe only what Mnemosyne itself owns, or every source it can read?) the operator should weigh in on if/when `hive-memory`'s role grows — not blocking this epic, which can ship a correct 0-4 model without answering it.

**OQ2 — Should the canonical taxonomy module (`ml-01`) live in `lib/mnemosyne/layer1/` (alongside the existing tier/Level-0 code, despite the naming collision research-brief.md §0 already flagged) or a new top-level module (e.g. `lib/mnemosyne/memory-levels/`)?** This plan's stories (§ vertical-plan.md) propose a new top-level module specifically to AVOID compounding the `layer1`/`layers` naming collision already identified as part of the miscommunication — but naming this repo's modules is a real, visible decision the operator may have a preference on that this pass didn't have access to ask about. Flagged rather than treated as fully closed.

**OQ3 — Long-term: should the retrieval-cascade config (`MNEMOSYNE_LAYERS`) itself eventually be re-keyed to reference canonical level numbers (e.g. `{level: 2, name: 'graphify'}`) rather than bare adapter names?** Out of scope for this epic (§5 deliberately keeps `GET /layers` byte-for-byte unchanged), but a natural next question once both models exist side by side. Not resolved here — a real design question for a future epic once operators have lived with both surfaces for a while.

## 9. Risks

| Risk | Mitigation |
|---|---|
| A new `GET /memory-levels` route + renamed UI panel could still read as "yet another layer numbering scheme" if the copy isn't unmistakably clear about the distinction from both the orchestration tiers and the retrieval cascade. | Every UI/doc surface this epic touches must state the distinction explicitly (§5's UI copy requirement is an acceptance criterion, not a suggestion) — checked in `ml-06`'s review step. |
| `mnemosyne.md`'s install mechanism (§4c/§7.1) reuses `spliceManagedBlock`, which is already tested against clean and marker-free real files — but never yet against a THIRD composed source (Level 0 + Level 1 + tier, all three real, in one managed block) at once. | `ml-03`'s acceptance criteria require a real three-source composition test (not just Level-0-plus-tier, which already exists), verifying ordering and idempotency with all three present. |
| The Level 4 sub-index (§6) could silently return stale results if a file changes after being indexed and before the next rebuild. | Sub-index entries carry the same `sha256` content-hash convention `FileLayerAdapter` already computes per line/file; a hash mismatch at query time is a documented, explicit degrade-to-full-walk for that file, never a silently wrong cached hit — required in `ml-06`'s (hash computation) and `ml-07`'s (query-time degrade) acceptance criteria. |
| Renaming the existing "Memory Layer Stack" panel to "Retrieval Layer Stack" could visually/behaviorally regress `pw-04`'s already-shipped, already-tested acceptance criteria (GET /layers reused as-is, Level 0 stays view-only). | `ml-07` is a dedicated regression story: reruns/extends the existing layer-stack tests, asserts `GET /layers`'s route/response is byte-for-byte unchanged, and asserts no edit affordance was introduced anywhere near Level 0 in the rework. |
| Three independent "layer" vocabularies already exist in this codebase (research-brief.md §0); a 4th new route/module could add a 4th meaning if named carelessly. | `ml-01`'s taxonomy module and every doc this epic writes use "memory level" (never bare "layer") for the 0-4 model specifically, and explicitly cross-reference (not silently ignore) the other two existing meanings — `ml-09`'s doc-reconciliation story is the final check that this held throughout. |
| The Level 1 `mnemosyne.md` seed content (§4a, drawn from `MANDATE_SECTIONS`) could drift from `tiers.ts`'s own copy if both are hand-maintained independently going forward. | Resolved by `ml-02`'s design: `mnemosyne.md` becomes the new single source; `tiers.ts`'s `MANDATE_SECTIONS` is updated to read from it (or `ml-02` documents, as an explicit acceptance criterion, exactly which one is now canonical) rather than leaving two independently-editable copies of the same mandate text. |

## 10. Dependencies

- Existing, unchanged: `level0.ts`, `block.ts`, `harness.ts`, `lock.ts` (all reused as-is by Level 1's extension); `GET /layers`, `client.getConfiguredLayers()`, every `lib/mnemosyne/layers/` adapter (all reused as-is, read-only, by `GET /memory-levels`); the 4-tier orchestration hierarchy (`tiers.ts`, `persona.ts`) — untouched.
- New: a canonical memory-level taxonomy module (`ml-01`) — the foundation every other story in this epic reads from.
- New: `mnemosyne.md` (repo-root file) + a reader analogous to `level0.ts` + `sync.ts` composition extension + install-mechanism regression tests (`ml-02`-`ml-04`).
- New: `GET /memory-levels` route + UI rework (rename existing panel, add new section) + regression proof that `GET /layers`/Level-0-view-only are unregressed (`ml-05`-`ml-07`).

- New: final doc reconciliation (supersede/correct `docs/layer-architecture-v2-plan.md` §1's conflated table; cross-link the new taxonomy) via `ml-09`, plus full-suite regression pass + version bump via `ml-10`.

## 11. Scale assessment

**Medium-to-large**, consistent with the task's own framing: three real, independently-architected deliverables (canonical taxonomy + Level 1 install mechanism, UI/route rework with a genuine architectural fork to resolve, Level 4 sub-index), each touching real backend code plus tests, plus a foundational module every other piece depends on and a closing documentation-reconciliation pass. Not "large" in the `mnemosyne-persona-wizard` sense (no multi-transport write-primitive fan-out, no LLM-interview mechanics) — concentrated, high-decision-density work rather than high-surface-area work. Proceeding to full horizontal/vertical planning below, matching the depth of both prior epics in this repo.

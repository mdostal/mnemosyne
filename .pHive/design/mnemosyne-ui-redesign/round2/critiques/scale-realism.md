# Scale Realism — Round 2 Critique

Lens: would each candidate's *structure* still hold up once the real Personas panel (~50% of this app's UI surface: glossary disclosure, group/filter toolbar, a tier-grouped table with inline draft-review rows, an 8-field draft form, a Retrieval Layer Stack table, and a Level 0 pointer block) and the real Graph panel (7 toolbar controls — focus-node input, Go, depth select, zoom in/out, Reset view, Show whole graph — plus a node inspector plus an SVG canvas) are dropped in at their true size and density? Read directly from the four current HTML files; no screenshots, no assumptions carried over from round 1 without re-verification.

All four files render the same underlying panel set (Liveliness, Settings, Lanes, Search, Graph, Operations, Personas, Memory Levels) with comparable data density, so the comparison below is a fair like-for-like read of structure only.

---

## Collapsible Clusters (hardened)

`collapsible-clusters-hardened.html`

**Round-1 fix verification — "missing status signal on collapse": FIXED, verified.**
Each `<summary>` now carries a `.cluster-status-dot` that lives in the summary itself, not inside the collapsible body — e.g. line 720: `<summary><span class="cluster-status-dot review" title="2 persona drafts need review"></span>Personas <span class="cluster-tagline">…</span></summary>`. Because this sits outside `.cluster-body`, it stays visible whether the `<details>` is open or closed — this is a real, structural fix, not cosmetic. Same pattern on `cluster-system` (dot `pass`, title "All System panels passing") and `cluster-memory` (dot `pass`). Headings are also restored: every panel inside a cluster keeps its own `<h2 class="panel-title">` (verified at lines 538, 549, 566, 615, 634, 670, 698, 724), so collapsing a cluster no longer collapses panel-level semantics along with it.

**At real scale:**
- The Personas panel gets its own cluster (`cluster-personas`, `nav-count` = 1, line 525), so it is never forced to share a `grid-2` two-column row with a neighbor — it renders full-width by default. The System cluster's `.cluster-body.grid-2` (line 533) puts the two light panels (Liveliness, Settings) side-by-side and lets `Operations` break out via `.panel-wide`; the Memory cluster's `.cluster-body` (no `grid-2`, line 611) stacks Lanes/Search/Graph/Memory-Levels full-width, which correctly avoids squeezing the Graph panel's own internal `#graph-body` flex layout into a half column. This is real, content-aware layout judgment, not a blanket template.
- The sticky `#cluster-nav` (line 521) collapses eight panels down to three jump targets (System/Memory/Personas) with per-cluster counts — a sane reduction in nav surface at this panel count, though it does mean you can no longer jump straight to "Graph" without first landing on the Memory cluster and scrolling.
- **Real caveat:** all three `<details>` ship `open` by default (`cluster-system … open`, `cluster-memory … open`, `cluster-personas … open`). At full Personas + Graph density, the *first paint* is exactly as long as the flat/jump-chips document — the whole value of "collapsible" is opt-in per session and requires the operator to manually close clusters they don't need. That's a defensible choice (start expanded, let people fold what they don't want), but it means the pitch "this structure absorbs scale" is only true after user action, not by default.
- The Graph panel here is the outlier of the four: `#graph-view` is a plain placeholder div (`[ node-link diagram — 640×480 viewBox ]`, line 685) rather than an actual inline `<svg>` with nodes/edges like the other three candidates. The surrounding structure (`#graph-toolbar` with all 7 real controls, `#graph-inspector`) is complete and would hold a real canvas fine, but as shipped this file doesn't demonstrate the canvas actually coexisting with toolbar + inspector at real content, which is a legitimate part of this lens.
- Personas content itself is fully real: grouped table with a `persona-group-header` row per tier, an inline `persona-draft-detail-row` expansion with Approve/Discard, an 8-field draft form, the Retrieval Layer Stack table, and the Level 0 pointer — all present and unclipped inside the single Personas cluster body.

## Sidebar Glanceable (hardened)

`sidebar-glanceable-hardened.html`

**Round-1 fix verification — "real ARIA tab semantics": FIXED, verified, but incomplete.**
`nav#panel-nav` now carries `role="tablist"` and `aria-orientation="vertical"`; each item is `role="tab"` with matching `id`/`aria-controls`/`aria-selected` (lines 469–497); each panel is `role="tabpanel"` with `aria-labelledby` and `tabindex="0"` (e.g. line 506). This is genuine APG tab markup, not a cosmetic label change. One residual gap for this lens: the JS (lines 923–936) only wires `click`, not arrow-key roving-tabindex, which the ARIA tabs pattern expects — with 8 real tabs (and more once other panels are added) a sighted mouse user is fine, but a keyboard/AT user only gets Tab-through-8-buttons rather than idiomatic arrow-key switching. Not disqualifying, but not fully "real ARIA tabs" either.

**Round-1 fix verification — "no-JS fallback": FIXED, verified.**
`<noscript><style>.panel { display: block !important; }</style></noscript>` (line 938) forces every panel visible if JS never runs. Combined with the tabs already being real `<button>` elements (not anchor-only), this removes the "basic navigability is load-bearing on script execution" risk that a structural-scale critique should care about.

**Round-1 fix verification — "color-semantics bug (review/fail badge)": FIXED for the badge, but the *underlying graph-node bug from the same family is still present, unfixed*.**
The persona status badges are now correctly distinct: `.status-badge.review { color: var(--accent); }` separate from `.status-badge.fail` (line 148) — so "needs review" reads amber, not red. However, the Graph panel's node-interaction CSS (lines 369–371) was **not** touched: `.graph-node.selected circle { fill: var(--fail); }` and `.graph-node.focus circle { stroke: var(--pass); }` — selection and focus states still directly reuse the red/green health tokens. That's outside what this round's fix note claims to have addressed, but it's the same defect class, and it matters more, not less, at real graph density: a 1,800-node impact graph will realistically need to show a genuinely-broken/orphaned node at the same time as a selected node and a focused node, and right now "selected" and "erroring" would render as the identical red circle.

**At real scale:**
- Structurally this is the strongest fit for "Personas is ~50% of the surface": only one `.panel.active` is ever in the DOM's visible flow (`display:none` on the rest, line 168), so the page's height is bounded by whichever single panel is open, never by the sum of all eight. Opening the dense Personas tab doesn't lengthen anything else, and leaving it immediately shrinks the page back down. This is the only one of the four candidates where Personas' real bulk cannot leak into the rest of the shell.
- The sidebar itself is a plain scrollable vertical list (`overflow-y: auto`, line 77) sized to content, so it will not itself become unwieldy as panel count grows.
- Trade-off inherent to the pattern, not a bug: the panel-nav status badges are the *only* glanceable signal once you're deep inside Personas — you cannot see Graph's or Operations' full detail without switching away, which is the classic single-active-panel cost. Given the lens is scale (not glanceability, which is a separate round-1 lens this candidate already won), this is a fair trade, not a defect.
- Personas content is real and complete (glossary `<details>`, group/filter toolbar, tier-grouped table with a `<form>` for draft propose/edit, Retrieval Layer Stack, Level 0 pointer) — same density as the other three, unclipped because it's the only thing rendered while active.

## Minimal Jump Chips (unchanged base)

`minimal-jump-chips-unchanged.html`

**No round-1 fixes applied — confirmed by direct read, and the "no fixes needed" framing does not hold up under this specific lens.**
This file is genuinely unmodified. Two things are worth separating:
1. It is missing `<!doctype html>`, `<html>`, `<head>`, and `<body>` (opens directly with an HTML comment then `<meta charset>`), and all three of its forms (`Add lane` line 559, `Search` line 580, `Save draft` line 878) use `<button type="submit">` inside a bare `<form>` with no `action`. These are real defects, but they belong to the build-feasibility lens the task summary references, not scale-realism per se — noted for completeness, not weighted into this ranking.
2. For *this* lens specifically: the hybrid candidate's own header comment (lines 27–43) directly quotes a round-1 scale-realism finding against this exact base — *"minimal-jump-chips's … has no collapse mechanism anywhere … no relief valve"* once Personas is realistically dense — and states it added one `<details>` specifically to answer that finding. A direct read of this file confirms the finding still applies verbatim: the only `<details>` present is `#personas-glossary` (a small definition list that predates this redesign), and the Personas panel's write-tooling (group/filter toolbar, tier-grouped table with inline draft-review row, the full 8-field draft form, Retrieval Layer Stack, Level 0 pointer) is **all** permanently expanded, all the time, alongside seven other full panels including Graph's toolbar+SVG+inspector. There is also no scroll-spy and no per-chip status indication (`grep` for `chip-pass`/`chip-fail`/`IntersectionObserver` returns nothing) — confirmed by the hybrid's own comment, which describes both as things it is *adding* on top of this base.
- At real Personas + Graph density this produces the single longest, most undifferentiated document of the four: one uninterrupted scroll from Liveliness through Memory Levels, ~940 lines of markup, with a sticky chip bar (line 596–605) whose only job is "jump to an anchor" — no indication of where you currently are, no indication of which panel needs attention, and nothing to fold away once you've looked at Personas or Graph.
- To be fair to the structural direction: chips + `scroll-margin-top` + `.panel-wide` grid rules are all present and correctly sized for Personas/Graph/Lanes/Search/Operations to run full-width (line ~151, `.panel-wide { grid-column: 1 / -1; }`), so nothing actually breaks or overflows — it is legible, just very long, with no relief valve at all. That is precisely what the round-1 finding said, and it is still true in this unchanged file.

## Hybrid (finalist-3 rings + finalist-2 graph colors)

`hybrid-rings-original-graph-colors.html`

This is minimal-jump-chips' structure with five targeted patches; the file's own header comment (lines 1–53) documents each one against the finding it answers, which made this easy to check point-by-point against the actual markup.

1. **Doc wrapper + `type="button"`: verified fixed.** Full `<!doctype html><html><head>…</head><body>` now present, and Personas/Lanes/Search's buttons are `type="button"` (line 989's `Save draft` is `type="button"`, not `submit`).
2. **Per-chip status rings, scale-realism ("no status-at-a-glance in the nav"): verified fixed, and verified honest.** `nav#jump-chips` links carry `chip-pass`/`chip-fail` only where a real `.panel-status` exists on that panel (Liveliness, Settings, Lanes, Personas → `chip-pass`; Memory Levels → `chip-fail`, matching its real `panel-status fail` "1 store degraded"; Search/Graph/Operations get **no** class because those panels genuinely carry no `.panel-status` line in this file) — confirmed by cross-referencing every `.panel-status` occurrence against every chip class. This is a real, load-bearing improvement for scale: at 8+ panels, an at-rest signal of "what needs attention" without opening anything is exactly what a flat, always-expanded document needs.
3. **Scroll-spy via IntersectionObserver: present, and correctly guarded** (`if (!('IntersectionObserver' in window)) return;`, line ~1066) — a real progressive enhancement, not load-bearing for basic use.
4. **Persona draft-tools `<details>` relief valve, scale-realism ("no relief valve"): partially fixed.** `<details id="persona-tools" open>` (confirmed) now wraps the draft form + Retrieval Layer Stack + Level 0 pointer, leaving the always-visible identity table untouched — a real, correctly-scoped structural improvement over the unchanged base. But like Collapsible Clusters' three `<details>`, this one also ships `open` by default, so the *first-load* length is identical to the unfixed base; the relief only activates once a user manually collapses it in-session, and there's exactly one relief valve for one panel — Graph's own toolbar+SVG+inspector block, Search's results table, and everything else remain permanently expanded with no fold option at all.
5. **Graph node + Memory Levels colors: only half-fixed, and the more relevant half (graph) is fixed in name only.** `.status-pill.degraded` (red) is now genuinely separated from `.status-pill.needs-review` (amber) — a real fix. But for the graph: `--node-selected: var(--fail); --node-focus: var(--pass);` (lines 71–72) — these are new *variable names* that alias directly back to the exact same red/green *values*. `.graph-node.selected circle { fill: var(--node-selected); }` therefore still renders literally identical red/green to a genuine pass/fail indicator anywhere else on the page. At a real 1,800-node graph where a selected node, a focused node, and a genuinely broken/orphaned node can coexist on screen, this reintroduces the same ambiguity the fix claims to resolve — it changed the token's name, not its collision with health-status meaning.

**At real scale, net:** structurally this inherits minimal-jump-chips' single biggest scale liability (one long always-expanded document with only one collapsible section) and only partially closes it — the chip-ring signal is a real win, the one persona `<details>` is a real but narrow and default-open relief valve, and Graph/Search/Operations get nothing. It is a genuine improvement over the unchanged base, but it does not reach either Collapsible Clusters' page-wide folding or Sidebar Glanceable's structural bound on rendered height.

## Ranking (scale realism only)

**1. Sidebar Glanceable (hardened)** — the only candidate whose structure *bounds* page height regardless of Personas/Graph density (`display:none` on inactive panels means the DOM's rendered bulk is always exactly one panel's worth, never the sum). Both round-1 fixes (ARIA tabs, no-JS fallback) verified real and load-bearing. Residual gaps (no arrow-key roving tabindex; the graph-node color bug from the same family as the fixed badge bug was left untouched) are real but secondary to the core structural property this lens is testing.

**2. Collapsible Clusters (hardened)** — the status-dot-on-summary fix is verified and genuinely solves "signal survives collapse," and cluster-to-content layout shows real judgment about which panels deserve `grid-2` vs full width at their actual size. Loses to #1 only because all three clusters default open (so first paint is full-length, same as the flat options, until a user acts) and because its Graph panel is a placeholder rather than a demonstrated real canvas — a completeness gap for this specific lens, not a structural one.

**3. Hybrid (rings + original graph colors)** — clearly better than the unchanged base it's built on: the chip status rings are real, verified, and honestly sourced only from real per-panel status; the one Persona `<details>` is correctly scoped. But it inherits the always-expanded-document liability everywhere except that one section, and its headline color fix (dedicated graph-node tokens) turns out to alias the exact same red/green values it was meant to move away from — a fix that changes the variable name, not the collision, at the exact place (a dense real graph) where that collision is most likely to matter.

**4. Minimal Jump Chips (unchanged base)** — confirmed, by direct re-read, to still have zero relief valves anywhere in the document and zero status signal in its nav chips. At real Personas + Graph density this produces the single longest, least differentiated page of the four, with nothing to fold, collapse, or hide. This is the same conclusion round 1 reportedly reached for this base under this lens, and nothing in the file has changed to revisit it — the "already the cleanest of the original 3" framing may hold for other lenses, but not for this one.
